# 异构小组混编策略

> Workshop 分组的最佳实践：通过刻意混编最大化学习效果

## 核心原则

**不要按经验水平或职能同质分组。** 混合不同背景的人可以：
- 经验者教新手 → 加深自己的理解
- 非技术人员提供业务视角 → PRD 质量更高
- 不同背景碰撞 → 更有趣的讨论和 Aha Moments

## 推荐分组矩阵

每组 3-4 人，确保覆盖以下维度：

| 维度 | 多样性要求 |
|------|-----------|
| AI 工具经验 | 至少 1 人有 AI 编程经验 + 至少 1 人是新手 |
| 技术深度 | 至少 1 人深度技术（架构/后端） + 1 人较浅 |
| 职能角色 | 尽量有 PM/业务 + 开发 + QA/测试的混合 |
| 性格特质 | 至少 1 人主动发言 + 1 人偏观察思考 |

## 分组实操流程

### Workshop 前（报名时收集）

报名表增加以下字段：

```
1. 你的主要角色: [PM / 架构师 / 后端开发 / 前端开发 / QA / DevOps / 管理者]
2. AI 编程工具使用经验: [从未用过 / 偶尔使用 / 日常使用]
3. AWS 经验: [初级 / 中级 / 高级]
4. 你更擅长: [动手写代码 / 产品思维 / 系统设计 / 测试质量]
```

### 分组算法（讲师手动）

1. 将所有人按 "AI 经验" 分为 3 档：专家 / 有经验 / 新手
2. 每组**必须**有 1 个"专家"或"有经验者"作为 **技术锚点**
3. 每组**尽量**有 1 个非开发角色（PM/QA/管理者）
4. 剩余人随机分配，平衡组间人数

### 开场时的角色分配

每组内分配 Workshop 角色：

| Workshop 角色 | 推荐人选 | 原因 |
|--------------|---------|------|
| PM (驱动 PRD) | 非技术人员或 PM | 练习业务思维，不被技术细节分心 |
| 架构师 | 有系统设计经验者 | 能评估方案合理性 |
| 开发 | AI 编程有经验者 | 能高效使用 Agent 完成实现 |
| QA/测试 | 任何人 | 好的学习机会，不需要预置技能 |

## 讲师分组速查

### 4 人/组 理想配置

```
┌─────────────────────────────────┐
│ 组长: AI 经验者（技术锚点）       │
│ 成员: PM/业务背景 1 人            │
│ 成员: 开发者 1 人（可以是新手）   │
│ 成员: QA/测试/其他 1 人           │
└─────────────────────────────────┘
```

### 3 人/组 最小配置

```
┌─────────────────────────────────┐
│ 组长: AI 经验者（兼架构师）       │
│ 成员: PM/业务（兼 QA 评审）       │
│ 成员: 开发者（主力实现）          │
└─────────────────────────────────┘
```

## 互助机制

- **先完成的组**可以派 1 人去支援未完成的组（"教练漫游"）
- 讲师可以临时调整：如果某组全卡住，从其他组借调技术锚点 5 分钟
- 设置公共求助频道（Slack/微信群），任何人都可以提问

## 常见问题

| 问题 | 解决方案 |
|------|---------|
| 某组全是新手，进度严重落后 | 讲师驻场 + 发放 fallback 模板跳过阶段 |
| 经验者包办一切，其他人旁观 | 强制角色分工：经验者只能指导，不能动手 |
| PM 角色觉得无事可做（开发阶段） | 让 PM 提前准备 Review Gate 评审标准 |
| 组内意见分歧 | 讲师仲裁或用 Party Mode 让 AI 给第三方建议 |
