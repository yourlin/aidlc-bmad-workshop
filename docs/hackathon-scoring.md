# Workshop 黑客松竞赛模式

> 适用版本：BMAD Method v6.8+ | 最后验证日期：2026-06-03

## 竞赛概述

将 Workshop 的产出作为竞赛评审对象，通过良性竞争激发参与度。各组在 AIDLC 流程结束后进行互评，设置多个奖项维度。

## 奖项设置

| 奖项 | 评判标准 | 谁来评 |
|------|---------|--------|
| 🏆 最佳 PRD | 需求完整性、清晰度、可操作性 | 全体投票 |
| 🏗️ 最佳架构 | 设计合理性、可扩展性、文档质量 | 讲师 + 架构师角色代表 |
| 💻 最佳代码 | 代码质量、测试覆盖、TDD 实践 | 其他组互评 |
| 🎯 最佳 AI 协作 | Prompt 质量、Agent 利用效率、Review Gate 执行 | 讲师评判 |
| ⚡ 最快完成 | 第一个通过 Review Gate #2 的组 | 自动记录 |

## 评分规则

### PRD 评分表 (10 分制)

| 维度 | 分值 | 评判要点 |
|------|------|---------|
| 完整性 | 3 | 功能需求是否覆盖所有核心场景 |
| 清晰度 | 3 | 非技术人员能否理解 |
| 可验证性 | 2 | 验收标准是否具体可测试 |
| AI 协作质量 | 2 | Prompt 是否有效引导 Agent 产出高质量内容 |

### 架构评分表 (10 分制)

| 维度 | 分值 | 评判要点 |
|------|------|---------|
| 技术合理性 | 3 | AWS 服务选型和设计模式是否合适 |
| 数据模型 | 3 | DynamoDB schema 是否支持所有访问模式 |
| 安全性 | 2 | 认证、授权、最小权限是否考虑 |
| 可观测性 | 2 | 监控、告警、日志是否规划 |

### 代码评分表 (10 分制)

| 维度 | 分值 | 评判要点 |
|------|------|---------|
| 可运行性 | 3 | 代码能否编译/运行通过 |
| 测试覆盖 | 3 | 是否遵循 TDD，测试是否有意义 |
| 代码质量 | 2 | 命名、结构、错误处理 |
| 模式一致性 | 2 | 是否遵循架构文档约定的模式 |

## 竞赛流程

```
时间线:
──────────────────────────────────────────────
正常 Workshop 流程 (完整 AIDLC)
──────────────────────────────────────────────
↓ 开发完成后 (Review Gate #2 之前)
──────────────────────────────────────────────
[5 min] 各组准备展示（选出 1-2 个亮点）
[15 min] 各组闪电展示（每组 2-3 分钟）
[5 min] 互评打分（扫码/举手/贴纸投票）
[5 min] 宣布结果 + 颁奖
──────────────────────────────────────────────
```

## 互评方式建议

1. **贴纸投票** — 每人 3 张贴纸，贴在最欣赏的组的白板上
2. **扫码评分** — 在线表单打分（适合远程）
3. **举手投票** — 最简单，当场举手选出每个奖项

## 讲师操作清单

- [ ] Workshop 开始时宣布竞赛规则和奖项
- [ ] 准备评分表（打印或在线链接）
- [ ] 记录各组 Review Gate 通过时间（最快完成奖）
- [ ] 闪电展示环节控时（严格 3 分钟/组）
- [ ] 准备小奖品或证书（可选）

## 注意事项

- 竞赛是辅助，不是主线 — 强调"最佳实践"而非"最快速度"
- 确保所有组都有获奖机会（设多维度奖项）
- 对于落后的组，给予鼓励性评价（如"最佳学习态度"）
- 避免让竞赛压力影响 Workshop 学习体验
