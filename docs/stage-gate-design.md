# 闯关模式设计（Stage Gate System）

> Workshop 流程的游戏化设计：5 个阶段关卡 + 通关条件 + 进度看板

---

## 总览

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  第 0 关  │───▶│  第 1 关  │───▶│  第 2 关  │───▶│  第 3 关  │───▶│  第 4 关  │
│ 环境就绪  │    │  PRD 完成 │    │ 架构完成  │    │ Sprint   │    │ 代码实现  │

    5 min           30 min          30 min          15 min          70 min
```

## 第 0 关：环境就绪

**通关条件：**
```bash
./verify-workshop.sh
# 输出: 🟢 环境就绪！
```

**具体检查项：**
- [ ] Node.js >= v20
- [ ] Python >= 3.10
- [ ] GitHub Token 已配置
- [ ] BMAD 已安装（`npx bmad-method status` 成功）
- [ ] AI IDE 可用

**通关标志：** 验证脚本输出全绿
**未通关处理：** 技术助教介入，其他组可先进入第 1 关

---

## 第 1 关：PRD 完成

**通关条件（Greenfield）：**
- [ ] `_bmad-output/planning-artifacts/prd.md` 文件存在
- [ ] PRD 包含至少 3 个 API 端点定义
- [ ] 每个端点有验收标准
- [ ] PRD 字数 > 200（不是空壳）

**通关条件（Brownfield）：**
- [ ] `_bmad-output/planning-artifacts/project-context.md` 已审核确认
- [ ] 增量 PRD 文件存在
- [ ] 增量 PRD 包含变更范围和验收标准
- [ ] 明确列出"不做什么"

**AI 辅助校验 Prompt（学员自检）：**
```
请检查 _bmad-output/planning-artifacts/prd.md 是否满足以下条件：
1. 是否有至少 3 个明确的 API 端点定义？
2. 每个端点是否有验收标准（可判断通过/不通过）？
3. 是否有非功能需求（性能、安全）？
4. 范围是否合理（4 小时内可完成的 MVP）？

如果有缺失，列出具体缺什么。
```

---

## 第 2 关：架构完成

**通关条件：**
- [ ] `_bmad-output/planning-artifacts/architecture.md` 文件存在
- [ ] 包含数据模型/Schema 设计
- [ ] 包含 API 路由定义
- [ ] 包含认证方案
- [ ] 与 PRD 的端点一致（无遗漏、无冲突）

**AI 辅助校验 Prompt：**
```
请交叉检查 PRD 和架构文档的一致性：
1. PRD 中的每个端点在架构中都有对应的路由和 handler 吗？
2. PRD 中的数据模型在架构的 schema 设计中被覆盖了吗？
3. 有没有架构中提到但 PRD 未定义的功能？
4. 非功能需求（性能指标、认证）在架构中有具体方案吗？

输出一致/不一致的对照表。
```

---

## 第 3 关：Sprint Plan 完成

**通关条件：**
- [ ] Sprint Plan 文件存在
- [ ] Story 拆分合理（每个 Story 可独立实现和测试）
- [ ] 至少有 2 个 P0 Story
- [ ] 每个 Story 有负责人标注
- [ ] 依赖关系清晰

**快速校验：** Sprint Plan 中 Story 数量 >= 3，且标注了优先级

---

## 第 4 关：代码实现

**通关条件（最终通关）：**
- [ ] 至少 1 个 API 端点代码已实现
- [ ] 实现的端点有对应的单元测试
- [ ] 测试可运行（即使不全部通过）
- [ ] 代码结构与架构文档一致

**加分项（非必须）：**
- [ ] 2+ 个端点实现
- [ ] E2E 测试存在
- [ ] IaC/CDK 代码存在
- [ ] 所有测试通过

## 进度看板设计

### 物理看板（推荐，低成本高可见度）

在会议室白板上画：

```
┌─────────────────────────────────────────────────────────────┐
│  Workshop 进度看板                                           │
├────────┬────────┬────────┬────────┬────────┬────────────────┤
│        │ 第0关  │ 第1关  │ 第2关  │ 第3关  │ 第4关          │
│        │ 环境   │ PRD    │ 架构   │ Sprint │ 代码           │
├────────┼────────┼────────┼────────┼────────┼────────────────┤
│ 第1组  │  ✅    │  🔄    │        │        │                │
│ 第2组  │  ✅    │  ✅    │  🔄    │        │                │
│ 第3组  │  🔴    │        │        │        │                │
│ 第4组  │  ✅    │  🔄    │        │        │                │
│ 第5组  │  ✅    │  ✅    │  🔄    │        │                │
│ 第6组  │  ✅    │  🔄    │        │        │                │
└────────┴────────┴────────┴────────┴────────┴────────────────┘

✅ = 通关    🔄 = 进行中    🔴 = 卡住
```

**操作方式：** 每组完成一个阶段后，组长上来移动便利贴/磁铁到下一列。

### 电子看板（备选）

如果有大屏可用，用简单 HTML 页面实时更新。或用 AWS 简易服务：
- S3 静态页面 + 手动 JSON 更新
- 或直接用 Notion / 飞书多维表格共享视图

## Review Gate 与闯关的关系

| 时间点 | 闯关检查 | Review Gate（两道工序） |
|--------|---------|------------|
| 第 1 关通关后 | AI 自检：PRD 完整性 | **Review Gate #1**：① Party Mode AI 交叉评审 → ② 全角色人工评审（放行闸） |
| 第 2 关通关后 | AI 自检：架构一致性 | 并入 Review Gate #1 一起评 |
| 第 4 关通关后 | AI 自检：代码可运行 | **Review Gate #2**：① Party Mode AI 交叉评审 → ② 全角色人工评审 + 演示 |

**关键区别：**
- **闯关检查** = AI 辅助自检，各组独立完成，不需要等其他组
- **Review Gate** = 由两道工序组成，不可省略：
  - **第一道（Party Mode）**：AI 交叉评审，"加速器"，快速捞出格式错位、字段缺失、端点数量对不上这类机器能发现的硬性冲突
  - **第二道（全角色人工评审）**：所有相关角色到齐后一起进行的人工评审，是决定能否放行的"闸门"——发现 AI 看不出的语义分歧（领域惯例、隐含假设、跨文档间接依赖），并验收本阶段产出

> ⚠️ **只跑 Party Mode 而跳过人工评审，等于让 AI 给 AI 的产出签字——这恰恰是 AIDLC 要避免的。** Party Mode 加速比对，人做最终验收。

## 讲师操作指南

1. **开场** 时解释闯关规则，展示进度看板
2. **过程中** 每 15 分钟扫一眼看板，关注 🔴 状态的组
3. **Review Gate 前** 确认大部分组已通关对应阶段
4. **如果某组落后太多** — 提供预填模板让其跳过当前阶段追上进度
5. **结束时** 根据看板总结各组完成度，肯定进度快的组，鼓励未完成的组
