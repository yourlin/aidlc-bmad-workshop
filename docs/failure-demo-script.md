# 失败演示脚本（反面教材）

> 讲师在讲解 AIDLC 方法论时使用（约 5 分钟）
> 目的：通过展示"不遵守流程"的后果，让学员理解为什么需要结构化工作流

---

## 演示 1：跳过 PRD 直接编码（3 分钟）

### 讲师话术

"让我给你们看一个真实场景——如果我们跳过需求阶段，直接让 AI 写代码会怎样。"

### 演示步骤

**1. 直接输入模糊需求：**

```
帮我写一个酒店预订系统的 API
```

**2. AI 会产出代码，但展示其问题：**

**讲师指出：**
- "看，AI 自行决定了数据模型——但它假设一个房间只能有一种价格，没考虑淡旺季差价"
- "认证方式它随意选了 Basic Auth，但我们需要 JWT"
- "它写了 5 个端点，但遗漏了可用性查询——这恰恰是最核心的功能"
- "错误处理只返回 500，没有有意义的错误码"

**3. 揭示核心问题：**

```
问题不是 AI 写的代码质量差——代码语法完美。
问题是 AI 不知道「正确」的定义是什么。

没有 PRD = 没有验收标准 = 无法判断对错
```

### 讲师总结

"这就是 Vibe Coding 的风险——代码能跑，但不一定是你要的。AIDLC 的 Inception 阶段（PRD）就是确保 AI 知道'正确'长什么样。

第五组的实践印证了这一点：他们发现跳步后'整个都跑偏了'。PRD 评审是 ROI 最高的环节——越前面越精确，后面成本越低。"

---

## 演示 2：不做 Review Gate 的连锁漂移（2 分钟）

### 讲师话术

"第二个反面案例——如果我们跳过 Review Gate，让 AI 一路做下去会怎样。"

### 演示步骤（可以用预录屏幕或实时演示）

**展示一段"连续开发无评审"的结果：**

```
Story 1: AI 创建了房间管理 API ✓ （看起来正常）
Story 2: AI 创建了预订 API ... 但它用了不同的数据模型命名规范
Story 3: AI 创建了可用性查询 ... 但它没读 Story 1 的 DynamoDB schema，
         自己设计了一个不兼容的查询模式
Story 4: AI 创建了认证 ... 但只加到了 Story 3 和 4，
         Story 1 和 2 没有认证保护
```

**讲师指出连锁问题：**

| Story | 问题 | 根因 |
|-------|------|------|
| 2 | 命名规范不一致 | 新 session 没有看到 Story 1 的代码模式 |
| 3 | 数据模型不兼容 | 没有评审确认 schema 一致性 |
| 4 | 认证覆盖不全 | 没有全局视角检查所有端点 |

### 讲师总结

"每个 Story 单独看都是'正确'的——它们各自通过了自己的测试。但合在一起就不一致了。

这就是为什么 Review Gate 必须同步、必须人工参与：
- **AI 没有全局视角**——每个 session 只看自己的上下文
- **一致性问题只有人能发现**——它不是 bug，是设计决策的不统一
- **越晚发现越贵**——第四组的实践中，Party Mode 三人独立发现了同一个 bug

AIDLC 的 Review Gate 就是防止这种'各自正确但整体不一致'的漂移。"

## 演示 3：做了 Party Mode 却跳过人工评审（2 分钟）

### 讲师话术

"前两个案例是'完全不做评审'。但更隐蔽、也更常见的失败模式是——**做了 Party Mode，AI 都说'通过'，于是直接进入开发**。我们来看看这会漏掉什么。"

### 演示步骤

**展示一组三份文档,字面上都'自洽':**

```
PRD：        定义了 DELETE /rooms/{id} 端点，描述为"删除房间"
架构文档：   设计的是软删除（设置 status=archived）
测试策略：   验收标准写"删除后 GET 返回 404"
```

**先跑 Party Mode：**

```
"Start Party Mode with John, Winston, and Quinn.
Review the PRD, Architecture and Test Strategy for consistency..."
```

→ Party Mode 报告：**"三份文档相互一致，端点数量对齐，字段匹配，未发现冲突。"** ✅（AI 给了绿灯）

**然后全角色坐下来人工评审，QA 提出一个问题：**

> "等等——'删除'到底是物理删除还是归档？架构做的是软删除，但测试写的是删除后返回 404。如果是软删除，资源其实还在，语义上应该返回 **410 Gone**（曾存在、已归档），而不是 404（从未存在）。这三方对'删除'这个词的理解根本不一样。"

**讲师指出：**

| 文档 | 对"删除"的理解 | 隐含的 GET 行为 |
|------|--------------|----------------|
| PRD | 没说清物理还是逻辑 | 模糊 |
| 架构 | 软删除（status=archived） | 应返回 410 |
| 测试 | 当成物理删除 | 写成 404 |

**对齐决策（人工评审产出）：** 采用软删除，端点语义调整为"归档",测试标准改为"归档后 GET 返回 **410 Gone 并包含 archivedAt 时间戳**"。

### 讲师总结

"注意：**Party Mode 没报错,因为三份文档字面上都自洽**——端点都在、字段都对。分歧藏在对'删除'一词的**语义理解**里,这种'对得上但错了'的问题,只有具备业务经验的人能发现。

这就是为什么 Review Gate 是**两道工序**:
- **第一道 Party Mode** = 加速器,快速捞出'对不上'的硬性冲突
- **第二道全角色人工评审** = 放行闸,捕获 AI 看不出的语义分歧

**只跑 Party Mode 而跳过人工评审,等于让 AI 给 AI 的产出签字——这恰恰是 AIDLC 要避免的。** 这个分歧在 Inception 阶段解决只需改几行文档;如果流入 Construction,已写的代码和测试都要返工。"

---

## 演示效果预期

演示后学员应该理解：

1. ✅ **跳过 PRD 的代价**：AI 产出看起来对但不一定符合业务意图
2. ✅ **跳过 Review Gate 的代价**：多 Story 之间会产生设计漂移
3. ✅ **只跑 Party Mode 跳过人工评审的代价**：AI 看不出语义分歧，等于让 AI 给 AI 签字
4. ✅ **流程的价值**：不是"官僚主义"，而是"保证一致性的最低成本手段"
5. ✅ **动力**：带着"我不想在自己项目上犯这种错误"的心态进入实操
