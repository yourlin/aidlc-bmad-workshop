# 失败演示脚本（反面教材）

> 讲师在讲解 AIDLC 方法论时使用（约 5 分钟）
> 目的：通过展示"不遵守流程"的后果，让学员理解为什么需要结构化工作流

---

## 演示 1：跳过 PRD 直接编码（3 分钟）

### 讲师话术

"让我给你们看一个真实场景——如果我们跳过需求阶段，直接让 AI 写代码会怎样。"

### 演示步骤

**1. 直接输入模糊需求：**

```
帮我写一个酒店预订系统的 API
```

**2. AI 会产出代码，但展示其问题：**

**讲师指出：**
- "看，AI 自行决定了数据模型——但它假设一个房间只能有一种价格，没考虑淡旺季差价"
- "认证方式它随意选了 Basic Auth，但我们需要 JWT"
- "它写了 5 个端点，但遗漏了可用性查询——这恰恰是最核心的功能"
- "错误处理只返回 500，没有有意义的错误码"

**3. 揭示核心问题：**

```
问题不是 AI 写的代码质量差——代码语法完美。
问题是 AI 不知道「正确」的定义是什么。

没有 PRD = 没有验收标准 = 无法判断对错
```

### 讲师总结

"这就是 Vibe Coding 的风险——代码能跑，但不一定是你要的。AIDLC 的 Inception 阶段（PRD）就是确保 AI 知道'正确'长什么样。

第五组的实践印证了这一点：他们发现跳步后'整个都跑偏了'。PRD 评审是 ROI 最高的环节——越前面越精确，后面成本越低。"

---

## 演示 2：不做 Review Gate 的连锁漂移（2 分钟）

### 讲师话术

"第二个反面案例——如果我们跳过 Review Gate，让 AI 一路做下去会怎样。"

### 演示步骤（可以用预录屏幕或实时演示）

**展示一段"连续开发无评审"的结果：**

```
Story 1: AI 创建了房间管理 API ✓ （看起来正常）
Story 2: AI 创建了预订 API ... 但它用了不同的数据模型命名规范
Story 3: AI 创建了可用性查询 ... 但它没读 Story 1 的 DynamoDB schema，
         自己设计了一个不兼容的查询模式
Story 4: AI 创建了认证 ... 但只加到了 Story 3 和 4，
         Story 1 和 2 没有认证保护
```

**讲师指出连锁问题：**

| Story | 问题 | 根因 |
|-------|------|------|
| 2 | 命名规范不一致 | 新 session 没有看到 Story 1 的代码模式 |
| 3 | 数据模型不兼容 | 没有评审确认 schema 一致性 |
| 4 | 认证覆盖不全 | 没有全局视角检查所有端点 |

### 讲师总结

"每个 Story 单独看都是'正确'的——它们各自通过了自己的测试。但合在一起就不一致了。

这就是为什么 Review Gate 必须同步、必须人工参与：
- **AI 没有全局视角**——每个 session 只看自己的上下文
- **一致性问题只有人能发现**——它不是 bug，是设计决策的不统一
- **越晚发现越贵**——第四组的实践中，Party Mode 三人独立发现了同一个 bug

AIDLC 的 Review Gate 就是防止这种'各自正确但整体不一致'的漂移。"

---

## 演示效果预期

演示后学员应该理解：

1. ✅ **跳过 PRD 的代价**：AI 产出看起来对但不一定符合业务意图
2. ✅ **跳过 Review Gate 的代价**：多 Story 之间会产生设计漂移
3. ✅ **流程的价值**：不是"官僚主义"，而是"保证一致性的最低成本手段"
4. ✅ **动力**：带着"我不想在自己项目上犯这种错误"的心态进入实操
