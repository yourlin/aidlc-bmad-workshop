# PM 审阅指南

> 帮助非技术背景的 PM 理解和审阅 BMAD 技术产出物

---

## 你需要审阅什么？

在 AIDLC 流程中，PM 主要审阅以下产出：

| 产出物 | 你的关注点 | 你不需要关注的 |
|--------|-----------|---------------|
| PRD | 需求完整性、用户场景、验收标准 | 具体实现方式 |
| 架构文档 | 业务约束是否被尊重、性能影响 | 代码结构、API 细节 |
| Sprint Plan | Story 优先级是否正确、范围是否合理 | 时间估算、技术依赖 |
| 代码评审 | 功能是否符合 PRD 预期 | 代码风格、命名规范 |

---

## PRD 审阅 Checklist

### 业务完整性
- [ ] 所有核心用户场景都被覆盖了吗？
- [ ] 用户旅程中有没有断裂的环节？
- [ ] 边界情况（错误、异常、空数据）有没有考虑？
- [ ] 是否有遗漏的干系人需求？

### 验收标准
- [ ] 每个功能都有明确的"完成"定义吗？
- [ ] 验收标准是否可测试（有人能根据它判断"通过/不通过"）？
- [ ] 非功能需求（速度、安全、可用性）有明确指标吗？

### 范围控制
- [ ] 范围是否合理（不过大导致做不完，不过小缺乏价值）？
- [ ] "不做什么"是否明确列出？
- [ ] 有没有潜在的范围蔓延风险？

### Brownfield 特有
- [ ] 向后兼容性是否有风险？
- [ ] 已有功能是否会受到影响？
- [ ] 数据迁移计划是否安全？

---

## 架构文档审阅 Checklist

> 你不需要理解所有技术细节，关注以下业务影响：

### 业务约束
- [ ] 技术选择是否满足业务需求（性能、成本、时间）？
- [ ] 有没有引入未来难以更改的限制？
- [ ] 扩展性是否满足业务增长预期？

### 风险
- [ ] 有没有单点故障（一个东西坏了全部不可用）？
- [ ] 安全措施是否覆盖了敏感数据和操作？
- [ ] 出问题时有没有回退方案？

### 成本
- [ ] 运行成本是否在预算内？
- [ ] 有没有意外的高成本组件？

## "技术产出 → PM 可读摘要" 转换 Prompt

当你看到一份技术文档难以理解时，可以让 AI 帮你翻译。粘贴以下 prompt：

```
请把以下技术文档转换为 PM 可读的摘要版本。

要求：
1. 去掉所有代码和技术实现细节
2. 保留业务影响、用户影响、风险和约束
3. 用非技术人员能理解的语言
4. 标注需要 PM 决策的事项
5. 如果有技术选择对业务有影响，用"这意味着..."格式说明

文档内容：
[粘贴技术文档]
```

## 常见技术术语速查

| 技术术语 | PM 需要理解的含义 |
|---------|-----------------|
| API 端点 | 系统提供的一个功能入口（类似"窗口"） |
| 向后兼容 | 新改动不会破坏已有功能 |
| 数据库迁移 | 修改数据存储结构（有风险，需要计划） |
| 单元测试 | 自动化检查代码是否正确 |
| TDD | 先定义"正确"是什么，再写代码 |
| Sprint | 一个开发周期（通常 1-2 周） |
| Story | 一个独立可交付的功能单元 |
| IaC | 用代码管理服务器（可重复、可追溯） |
| Review Gate | 质量检查点（必须通过才能继续） |

## 如何提反馈

审阅后如果有问题，用以下格式反馈给技术团队：

```
【反馈类型】需求遗漏 / 理解偏差 / 风险疑问 / 优先级调整

【具体位置】PRD 第 X 节 / 架构文档 XX 部分

【我的理解】我认为这里应该是...

【疑问/建议】为什么选择这个方案？是否考虑过...？
```

这样格式化的反馈能帮助技术团队快速理解你的关注点。
