什么是 AIDLC？

AIDLC（AI-Driven Lifecycle）是一套 AI 驱动的软件开发全生命周期方法论，结合 BMAD（Build More Architect Dreams）— AI 驱动的敏捷开发框架，具有规模自适应智能，提供 12+ 专业化 Agent 和 34+ 工作流。

🎯

Inception（需求）

PM 创建 PRD，QA 编写测试策略。AI Agent 引导结构化思考。

⚡

Construction（构建）

PM、架构、开发、测试 4 角色并行。AI 生成代码和测试，人工 Review。

🚀

Operations（运维）

CDK 定义基础设施，CloudWatch 监控，IaC 确保环境一致性。

"AI is not Google. The AI is a facilitator — every module becomes a master facilitator to bring the best out of you."

—— Brian · BMAD 作者

🛡️ Brownfield 项目注意事项

内置 workflow 生成的 project-context.md 记录技术栈与受保护路径约束，以下是额外提醒

🚫 AI 不可以做

• 删除/重命名已有文件
• 修改已有 API 格式
• 破坏性 schema 变更
• 引入冲突依赖
• 跳过 lint/test 规则

✅ AI 必须做

• 先读代码再动手
• 匹配已有代码风格
• 变更必须有测试
• 已有测试全部通过
• Feature Flag 包裹新功能

👤 你需要做

• 调用内置 skill 生成项目文档与上下文
• 审核 skill 产出 + 补充业务描述
• 在 project-context.md 标注受保护目录
• 开始前跑通已有测试
• Review Gate 更严格
💡 bmad-document-project + bmad-generate-project-context 扫描代码后把技术栈与约束写入 project-context.md，后续标准 Agent 自动加载。
你只需审核产出、补充业务描述、标注受保护路径即可。

👥 多人团队协作

核心原则：规划收敛、实施发散 — Phase 1-3 一人主笔，Phase 4 按 Epic 并行

分阶段策略

Phase 1-2（Analysis/PRD）：1 Tech Lead 主笔，团队评审
Phase 3（Architecture）：架构 + UX 可并行，Epic 拆分等二者完成
Phase 4（Implementation）：按 Epic 分配，每人独立 context

推荐：Epic 级分工

Epic 1 用户认证 → 开发者甲
Epic 2 订单管理 → 开发者乙
Epic 3 支付集成 → 开发者丙
✓ context 独立 · 冲突少 · 责任清晰

5 个必须同步的时机

1️⃣ PRD 完成 — 全员 review
2️⃣ Architecture 完成 — 全员 review
3️⃣ Sprint Planning — 认领 story
4️⃣ Epic Retrospective — Party Mode
5️⃣ Course Correction — 需求/架构变更

4 个反模式

❌ 多人各自跑 Mary 头脑风暴
❌ 每人写自己的 architecture.md
❌ A 写 story，B 直接改
❌ 多人共享同一 Agent 会话
推荐角色分配（3-6人）：1 Tech Lead（Phase 1-3 主笔）+ 2-4 开发者（Phase 4 分 Epic）+ 1 QA Lead（审全员 PR）

❓ 常见问题

必须使用 Kiro 吗？▶
推荐 Kiro（AWS AI IDE，内置 Spec Driven），但 Claude Code、Cursor、CodeX 同样兼容。核心差异在于 Kiro 的 Agent 协作和 Review 工作流更原生。
没有安装 BMAD 怎么办？▶
直接使用 Seed Prompt 文件中的内容，手动粘贴到 AI IDE。BMAD 安装是可选增强。
一个人可以扮演多个角色吗？▶
可以。使用 Party Mode 在同一终端切换不同 Agent。人数不足时建议兼任相近角色（如 PM + 架构师）。
Workshop 时间不够怎么办？▶
应急方案：① 砍掉 IaC ② 开发只完成 1 个 Story ③ 使用预置 PRD 跳过生成。确保至少完成一次"AI 生成 → 人工 Review"循环。
Kiro Spec Driven 和 BMAD 什么关系？▶
同一哲学的不同维度。Kiro 在 IDE 层面确保"先规格再代码"；BMAD 在方法论层面确保"Agent 引导逐层精化"。结合 = 从想法到规格到代码的完整闭环。
Agent 响应太慢或出错？▶
① 切换 Quick Flow（Barry Agent）② 检查 API Key 配额 ③ 准备离线 mock 数据 ④ Party Mode 绕过卡住环节。
Day 2 小组分享怎么准备？▶
每组 10 分钟：2min 项目概述 → 4min 产出物演示 → 2min Aha Moment / 踩坑 → 2min Q&A。建议提前准备屏幕录制或截图。

🎓 深度答疑 — 实战中的高频追问

点击展开查看要点 · 源自真实客户提问

⚖️Vibe coding 还是 Spec driven？▶
"BMAD 这种重流程是不是会拖慢我们？到底该轻装快速迭代还是先写 PRD/架构？"
不是二选一，是一条连续谱。Vibe 适合探索/原型/个人，Spec driven 适合生产/团队/长期维护——误用比选错更危险。
  • 6 维度决策：项目寿命 · 团队规模 · 风险等级 · 领域清晰度 · 维护要求 · 知识传承
  • 5 个错配：生产代码上 Vibe（最致命）· 原型上强 Spec · 不清晰领域强 Spec · Brownfield 用 Vibe · 全阶段同一风格
  • 5 个梯位：Pure Vibe → Vibe+决策记录 → Hybrid → Spec 主导(BMAD) → Pure Spec
  • 迁移路径：Bug 频增/第二个工程师加入/客户真用 → 用 /bmad-document-project 反向生成 PRD
🧪BMAD 装好就能自动跑 TDD 吗？▶
"自带 QA / Test Architect personas，是不是装好就能自动测试驱动开发？"
BMAD 提供 TDD 脚手架，但跨 persona 的编排不会自动发生——你要像导演一样按序调出 Test Architect → 写 AC → Dev 实施。
  • 双层架构：内层 bmad-dev-story 自动 red-green-refactor；外层 TEA + Murat + 9 个 testarch skill（需人工触发）
  • 内层守门：不许跳 RED · 不许跳 task · 3 次失败强制 HALT
  • 7 阶段生命周期：PRD → Story → 测试设计 → 框架 → ATDD → 实施(自动) → 验证追溯
  • 三大教训：过程很重要 · 不能放任 Agent · Driver's Seat（责任永远在你）
🔗BMAD vs Superpowers 选哪个？▶
"两套功能看起来重叠不少（brainstorming/TDD/planning），到底选哪个，还是都装？"
两个都装，各管一段。BMAD 管"应该建什么"（前段：想法→dev-ready），Superpowers 管"应该怎么建"（后段：执行/TDD/调试/验证）。
  • 本质区别：BMAD = 方法论+Persona+项目本地；Superpowers = 单点 Skill 集合+全局
  • 3 个冲突点：写计划 · 头脑风暴 · TDD 强制（流程级 vs skill 级）
  • 推荐组合：启动(BMAD 主导) → 单 story 实施(Superpowers 主导) → 演化(BMAD 主导)
📋PRD 在 Jira、代码在 Git 怎么协同？▶
"PM 把 PRD 维护在 Jira，DEV/QA 在 BMAD 流程里根本看不到——Git 里没有 PRD。"
这是真实的工具链断层，不是配置疏忽。建议保留 Jira 作 PM 工作面，自动镜像 PRD 到 Git 作为 BMAD 输入。
  • 为何是真问题：BMAD 的 persistent_facts 期望 PRD.md 在文件系统，缺失会让 create-story/tea/dev-story/trace 全断
  • 4 层方案：PRD-as-Code → Jira→Git 自动同步(推荐⭐) → Jira MCP server → 手动导出
  • 集成点：activation_steps_prepend 钩子，跑 skill 前自动 sync
  • 角色分工：PM 守 Jira 不变 · DEV 跑 BMAD 自动 sync 不必去 Jira
🧩支持跨 repo？PRD↔架构有版本关联？▶
"项目涉及 2 个代码库，BMAD 支持跨 repo 吗？PRD 改了 Architecture 会自动失效吗？"
两问都是 ❌ 当前不直接支持，✅ 有 workaround。BMAD 绑定单一 {project-root}，PRD↔架构只记路径不记版本快照。
  • 跨 repo：47 个 skill 对 monorepo/multi-repo 零命中 → workaround：父目录合一 / 双装机 / monorepo 工具
  • 版本关联：只存路径到 inputDocuments[]，不存 PRD 的 hash/timestamp/commit
  • 官方 4 步兜底：逐条 ADR 映射 → check-implementation-readiness → correct-course → git 兜底
  • 底层：event-sourcing（append-only log），非 Git snapshot+hash
⚙️流程和角色行为能定制吗？▶
"开发流程能改成我们团队的样子吗？每个角色做什么、按什么规矩，能定制吗？"
角色 = 完全可定制（6 维度全开放），流程 = 部分可定制（挂自己 workflow/注入约束 ✅；改内置步骤序列 coming soon）。核心：per-agent override + 三层叠加，永不动源码。
  • 角色 6 维度：显示名 · persona · memories · menu · critical_actions · prompts
  • 流程两层：浅层（挂 workflow/注入约束/启动钩子）✅；深层（改内置步骤）⚠️ 用 BMad Builder 自造绕过
  • 三层叠加：Default → Team → Personal，升级覆盖源文件但保留 .customize.yaml
  • 铁律：只写 override 文件，绝不直接改 BMAD 源码
